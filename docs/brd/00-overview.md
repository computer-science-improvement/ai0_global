# BRD (as-is) — ai0_global: огляд продукту

> Статус: оновлено з коду 2026-10-10 (коміт 54dd1eb, гілка feat/editor-agent). Описує, як система **фактично** працює зараз. Власник перечитує й виправляє; розбіжності між «як є» і «як має бути» фіксуються в розділах «Спостереження» та «Відкриті питання» кожного документа.

## Що змінилось з 2026-10-05

- **Стратегії → серії агентів (spec 023).** Контент веде агент: серії в плейбуку, правила розкладу («піни») і єдиний журнал використаного контенту (`content_ledger`). `/app/strategies` тепер лише legacy: його видно тільки на перегляд, створювати й вмикати стратегії не можна. Стратегії, ще не перенесені в серії, крон запускає як і раніше. Видалення модулів стратегій (T7 фаза B) чекає рішення власника.
- **Режим апруву (spec 031).** Додано четвертий режим `approve` (між `shadow` і `live`). Він стоїть за замовчуванням для нових ресурсів: кожен пост агента чекає на апрув власника.
- **Незалежні ресурси та часові пояси (spec 024).** Meta/TikTok-акаунти більше не «дзеркала». Агент вирішує для кожного ресурсу, що з ідеєю робити: дублювати, адаптувати чи писати унікальний пост. У кожного ресурсу свій часовий пояс.
- **MANAGER: директива чи порада (spec 025).** Директива обовʼязкова: оркестратор може лише прийняти її або оскаржити. Порада необовʼязкова, її можна відхилити. Кожен тип директиви має виконавця в коді (`applied` / `verified`). `pause_resource` справді ставить ресурс на паузу.
- **Лендинг (spec 026).** Лендинг тепер позиціонує мережу як «A media network run by AI agents», лише англійською. Реклама замовляється через Telegram DM з атрибуцією джерела, є форма заявки, секція й сторінка `/white-label`. Особисту пошту з лендингу прибрано.
- **Конструктор навігації (spec 027).** Меню зібране з реєстру (10 груп, остання — «Legacy»). Пункти мають лічильники-бейджі. Є палітра ⌘K. Власник змінює меню в Settings → Navigation.
- **Автентифікація (spec 028).** Сесії тепер серверні: їх можна відкликати. nginx не віддає `/app/*` без сесії. Router guard замінив клієнтський редирект. Збірка без способу входу падає. Ліміт спроб входу живе в Redis, а кожна спроба пишеться в аудит.
- **Витрати на AI (spec 029).** Кожен виклик LLM пишеться в `llm_usage`. Додано сторінку `/app/spend`. Ліміти витрат за замовчуванням блокують виклики.
- **Єдине сховище даних (spec 032).** Контентні таблиці (рецепти, цитати, факти…) тепер є views над `data_items`. Додано сторінку `/app/data` з імпортом CSV/JSON без міграцій.
- **Rich-повідомлення Telegram (spec 033).** Агентські пости можуть іти через `sendRichMessage` (заголовки, списки, таблиці, формули). Якщо так не вийшло, пост відправляється звичайним HTML.
- **Модель за замовчуванням (spec 035).** Нова сторінка `/app/models`. Глобальна модель за замовчуванням — `z-ai/glm-5.3-flash` для всіх ролей. Модель і reasoning effort задаються для кожного агента окремо.
- **Якість текстів (spec 034, частково).** Готово T1 і T8. T1 — «voice core» у кожному промпті автора, детермінований slop-lint, гумор і сленг лише за дозволом власника. T8 — аудит скілів і тон-скіли ресурсів. T2/T3/T6 ще в роботі.
- **Інфраструктура.** Три середовища: local-development, dev-stage (автодеплой з `develop`) і production (теги `v*` з `main`). Міграцій тепер 65 (`001`–`066`, номера `048` немає).

## 1. Що це за продукт

ai0_global — система для власника мережі українських медіаресурсів: Telegram-канали, а також Instagram / Facebook / Threads, TikTok і YouTube як окремі ресурси. Мережа заробляє на рекламі. Система:

- **генерує й публікує контент через AI-агентів.** На кожну мережу є оркестратор, під ним планувальник, виконавець і рев'юер. Агент сам вирішує, що й коли публікувати, спираючись на плейбук, серії, датасети, історію й статистику. Власник керує розкладом через чат або вкладку Schedule. Старі крон-стратегії ще працюють там, де їх не перенесли в серії;
- **керує мережею агентів**: MANAGER над оркестраторами (директиви й поради), крос-промо між ресурсами;
- **рахує витрати на AI**: кожен виклик LLM пишеться в журнал з ціною; ліміти витрат за замовчуванням блокують виклики;
- **збирає аналітику** власних і відстежуваних каналів (підписники, перегляди, ER) та шукає нові канали й ніші;
- **продає рекламу**: лендинг із медіакітом, замовлення через Telegram DM або форму заявки, оплата через LiqPay, публічні звіти для рекламодавців.

**Продуктове рішення власника (2026-06):** це мережа, якою керує сам власник, а **не SaaS**. Немає мультитенантності, один оператор, один екземпляр сервісу автоматизації. Координація публікацій живе в памʼяті процесу, тож другий екземпляр призведе до подвійних публікацій. Лендинг пропонує white label лише як окремий екземпляр під клієнта (spec 026).

## 2. Користувачі та ролі (as-is)

| Роль | Де | Як потрапляє |
|---|---|---|
| Власник / оператор | `/app/*` (дашборд) | `/login`: токен доступу або Telegram Login Widget (спосіб задається при збірці); сесія на сервері |
| Відвідувач / потенційний рекламодавець | `/`, `/white-label` | без логіну; може залишити заявку на рекламу чи white label або відкрити Telegram DM |
| Рекламодавець | `/report/$token` | за секретним посиланням на звіт |
| Підписники ресурсів | Telegram / Meta / TikTok / YouTube | не взаємодіють із дашбордом; їхні дії (вступи за інвайт-посиланнями, кліки `/r/:code`) збираються для KPI |
| Скрипти, MCP-сервер редактора | API | заголовок `Authorization: Bearer <TRACKING_TOKEN>`; сесії не створюють |

Ролей усередині дашборду немає: хто увійшов, той бачить і може все.

| Компонент | Технології | Роль |
|---|---|---|
| `apps/dashboard` | React 19, TanStack Router/Query, Vite 8, Tailwind v4 (темна тема) | інтерфейс власника, публічний лендинг, `/white-label`, звіти |
| `apps/automation` | NestJS 10, raw `pg`, BullMQ/Redis | API, крони, AI-агенти, публікація, збір статистики, журнал витрат |
| `apps/automation/editor-skills` | Markdown | вбудовані скіли агентів (синхронізуються в БД із версіями) |
| `apps/pipeline` | Node-скрипти | офлайн-парсинг і скрейпінг датасетів → `data_items` через `loadData()` |
| Postgres 16 | 65 міграцій `database/migrations/001`–`066` (номера `048` немає) | усі дані |
| Redis | BullMQ, ліміт спроб входу | черги задач |
| nginx (контейнер `dashboard`) | `auth_request` | віддає SPA; `/app/*` лише з дійсною сесією; проксить API-префікси й `/r/` на automation |
| `backup` | — | резервні копії БД |

**Середовища** (`NODE_ENV`): `local-development` (з вихідного коду), `dev-stage` (автодеплой з гілки `develop`, окремий бот і тестовий канал), `production` (деплой за тегом `v*.*.*` з `main`). Workflows лежать у `.github/workflows/`, runbook — у `docs/runbooks/dev-stage-server-setup.md`.

**Зовнішні інтеграції:**
- Telegram Bot API: публікація, у тому числі `sendRichMessage` з Bot API 10.1 з відкатом на HTML; адмін-бот; `chat_member`;
- MTProto-сесії: статистика, читання каналів, DM-агент;
- Meta Graph (Instagram, Facebook, Threads), TikTok, YouTube (дані для лендингу й дайджесту);
- Telegraph (лонгріди);
- LLM: OpenRouter для всіх агентів (за замовчуванням `z-ai/glm-5.3-flash`, вибір на `/app/models`). Старі стратегії й допоміжні сервіси ще ходять напряму в Claude / OpenAI / Perplexity / Grok і в Claude Agent SDK (тематична маршрутизація, семантичний дедуп). Витрати всіх цих викликів пишуться в `llm_usage`;
- публічний каталог моделей OpenRouter (`/api/v1/models`, без ключа);
- LiqPay (оплата реклами).

Токени зберігаються зашифрованими (AES-256-GCM, ключ `TOKEN_ENCRYPTION_KEY`).

## 5. Ключові наскрізні процеси

1. **Контент від агентів (основний шлях).**
   - Оркестратор мережі веде плейбук: розділи ресурсів, формати, частоту, серії. Серія — це регулярна рубрика з каденцією, часом і джерелом (датасет, RSS, API, дайджест мережі).
   - Власник може задати правила розкладу: частоту, «чорні» вікна та піни (пост у конкретний час). Серію, яку створив або змінив власник, заблоковано від змін агентом.
   - Планувальник будує план дня. Для кожного ресурсу він вирішує, що робити з ідеєю: `duplicate`, `adapt` чи `unique` (spec 024).
   - Виконавець пише PostSpec, проходить lint і guards. Далі все залежить від режиму: `shadow` дає лише превʼю, `approve` ставить пост чекати на апрув, `live` публікує.
   - Використане джерело фіксується в `content_ledger`, щоб контент не повторювався. → документи 03, 04
2. **Legacy-стратегії.**
   - Привʼязки `strategy_bindings`, які ще не перенесено в серії, крон публікує без рев'ю, як раніше.
   - Перенесення робиться кнопками на `/app/strategies`: Migrate → апрув чернетки плейбука → Cutover. Rollback повертає стратегії. → документ 02
3. **Чат з агентами.** Власник просить пост або зміну розкладу. Агент готує чернетку чи картку дії. Публікація, планування і зміни розкладу відбуваються лише за кнопкою або явною командою. Через `@handle` можна звернутися до конкретного агента. → документи 03, 04
4. **Мережа агентів.**
   - MANAGER кілька разів на день читає KPI-дайджест і видає оркестраторам директиви або поради.
   - Структурні директиви спершу йдуть власнику на картку. Оскаржені директиви вирішує власник.
   - Крос-промо працює через трекінгові інвайт-посилання.
   - Скіли версіонуються, з автовідкатом. → документ 04
5. **Аналітика, розвідка, витрати.** Статистика власних і відстежуваних каналів, граф каналів, рекомендації (документи 05, 06). Журнал `llm_usage` і ліміти `llm_budgets` — `/app/spend`.
6. **Реклама.**
   - Заявка з лендингу через Telegram DM з атрибуцією або через форму. Далі — замовлення та інвойс LiqPay, вебхук оплати.
   - Розміщення публікується в зарезервованому слоті, потім формується публічний звіт. → документ 08

## 6. Наскрізні бізнес-правила (as-is)

- `BR-GEN-01` Часи для власника — київські (`Europe/Kyiv`). Власні часи ресурсу (слоти, тихі й найкращі години, серії, денна статистика) — у його часовому поясі, за замовчуванням Київ. Пояс береться з картки Telegram-каналу, далі з профілю ресурсу, далі Київ. Інтерфейс показує обидва часи, коли вони різні (spec 024 FR-005). Доба для витрат і лімітів — київська.
- `BR-GEN-02` Дашборд `/app/*` віддається лише з дійсною сесією. У production nginx перевіряє її через `GET /auth/check` ще до HTML, далі router guard. Без сесії відбувається редирект на `/login?next=…`. Локальний обхід автентифікації можливий лише за `ALLOW_NO_AUTH=true`, `NODE_ENV` ≠ `production` і незаданого `TRACKING_TOKEN`. Production-збірка дашборду без способу входу падає (spec 028).
- `BR-GEN-03` Сервіс автоматизації запускається в одному екземплярі; паралельні екземпляри не підтримуються.
- `BR-GEN-04` Токени платформ зберігаються в БД зашифрованими; якщо зашифрованого токена немає, використовується значення зі змінних середовища.
- `BR-GEN-05` Агент має чотири режими: `off`, `shadow`, `approve`, `live`. Ефективний режим — нижчий із режимів оркестратора й картки. У `shadow` нічого не публікується. У `approve` кожен пост чекає на апрув власника. У `live` агент публікує сам. Публікація можлива лише після lint і guards: пауза каналу чи ресурсу, журнал використаного контенту, ліміт витрат.
- `BR-GEN-06` Агенти на пряме запитання не приховують, що вони AI; тон спілкування професійний і по суті.
- `BR-GEN-07` MANAGER видає директиву (обовʼязкову) або пораду (необовʼязкову). Структурні директиви — нові формати, зміна частоти на ≥30 %, крос-промо, пауза ресурсу, нова стратегія — потребують підтвердження власника через картку. Оркестратор може оскаржити директиву лише з причин owner rule / safety / capability / health, і тоді рішення за власником (spec 025).
- `BR-GEN-08` Увесь текст інтерфейсу (дашборд, лендинг, тексти бекенду, які показує UI) — англійською. Контент постів і промпти агентів лишаються українською (рішення власника 2026-10-06).
- `BR-GEN-09` Новий ресурс стартує в режимі `approve`. Перемкнути його на `live` може лише власник (spec 031).
- `BR-GEN-10` Кожен виклик LLM пишеться в `llm_usage` з токенами й ціною. Ліміти (`AI_DAILY_BUDGET_USD` — загальний, `EDITOR_DAILY_BUDGET_USD` — агенти, `EDITOR_CHANNEL_DAILY_BUDGET_USD` — ресурс, а також ліміт окремого агента) за замовчуванням блокують виклики після перевищення до київської півночі або до підняття ліміту (spec 029).
- `BR-GEN-11` Модель агента обирається так: власна модель агента (рольові агенти успадковують модель оркестратора) → legacy-перевизначення картки → env `EDITOR_MODEL_<ROLE>` → глобальна модель `ai.default_model` → вбудована `z-ai/glm-5.3-flash` (spec 035).
- `BR-GEN-12` Використаний контент для всіх шляхів публікації (агенти, чат, апрув, платформи, legacy-стратегії) записується в один журнал `content_ledger`. Правила повторного використання задає схема датасету (spec 023).

## 7. Глосарій

| Термін | Значення |
|---|---|
| Ресурс | один канал чи акаунт на платформі (`telegram:@key`, `instagram:<uuid>`, `tiktok:<uuid>`, `youtube:<uuid>`) |
| Мережа (network) | група ресурсів (`meta_account_groups`), якою керує оркестратор якірного Telegram-каналу |
| Плейбук | версійований план мережі: розділи ресурсів, формати, частоти, серії, правила |
| Серія | регулярна рубрика в плейбуку: каденція, час, ресурс, формат, джерело; може бути заблокована власником |
| Правило розкладу | частота, «чорне» вікно або пін (пост у конкретний час), який задав власник (`schedule_rules`) |
| Стратегія (legacy) | старе правило «що, звідки, коли й куди» з крон-розкладом (`strategy_bindings`); переноситься в серії |
| Картка редактора | налаштування агента для Telegram-каналу (`editor_channels`) |
| Слот | запланована позиція в денному плані (`editor_slots`) |
| PostSpec | структурований опис посту (формат, тіло, медіа, опитування, кнопки, rich-блоки) |
| Off / Shadow / Approve / Live | режим агента: вимкнено / лише превʼю / кожен пост чекає на апрув / автономна публікація |
| Скіл | Markdown-інструкція для агента (у файлі або в БД з версіями) |
| Директива / порада | обовʼязкова / необовʼязкова вказівка MANAGER оркестратору |
| Датасет | набір записів у `data_items` зі схемою `data_schemas` (рецепти, цитати, факти…) |
| Журнал контенту | `content_ledger`: що з якого джерела вже використано на якому ресурсі |
