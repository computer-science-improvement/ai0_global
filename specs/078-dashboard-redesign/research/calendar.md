## Calendar (/app/calendar): verified brief for the spec

### 0. Summary
- The calendar page is feasible **with no backend change for read-only (PR 6)**. The best data source is **not** what the handoff names.
- `GET /api/schedule/upcoming?hours=120` is clamped to **72 h and ≤50 items**, future only (`editor/schedule/upcoming.ts:47-48,65`). Do not use it.
- The existing per-agent range endpoint `GET /api/agents/:handle/schedule?from=&to=` (`schedule.controller.ts:26-29`, ≤14 days) already merges series/pin projections with active-plan slots.
- A pure merger already exists: `cellEntries(schedule, ref, date)` in `apps/dashboard/src/lib/schedule-grid.ts:36-81`. The per-agent week grid in `components/agents/AgentSchedule.tsx:134-200` (WeekGrid/Lane/EntryPill, which links to the slot page) is the closest existing UI.
- "Pipelines" has no data: legacy strategies were removed (`config/api/strategies.controller.ts:20-23`).
- "Ask the agent" has no draft-from-text HTTP route. A one-off **pin rule** is the working route.

For a card in another zone, an 'Ask the agent' pin at '12:00' runs at 12:00 resource time, and columns can be off by a day. Convert, or label the field with the resource's zone.
- One-off pin edge cases: (1) A pin dated today with a time already past is saved with no error, but materialiseAgent skips at <= now (schedule.service.ts:269-270). It never becomes a slot and shows as 'not planned'. Block past times on the client, or require at least now + a few minutes. (2) Pins count toward per_day. effectivePerDay subtracts the day's materialised pins (schedule-rules.ts:156, plan-schedule-rules.ts:257), so on days not yet planned a pin replaces one of the planner's own posts instead of adding one.
- Reserved slots: schedule slots[] includes kind 'reserved', which cellEntries maps to EntryKind 'reserved' (lib/schedule-grid.ts:45-46). These come from chat drafts scheduled via POST /api/editor/drafts/:id/schedule (drafts.service.ts:304-307, topic 'Чат: …'), paid sponsor ads and promo (flag `promo`). Neither the six-entry legend nor the §2 table maps them. The spec must decide, e.g. show chat drafts as 'yours' and ads as 'reserved'.
- 'Pipelines' replacement: the one non-agent source with a future schedule is paid ad orders. GET /api/ad-orders (payments/ad-orders.controller.ts:17; dashboard api/ads.ts:15) returns `publish_at`, `channel_id` and `editor_slot_id`. A digest-sponsor order turns into a reserved slot only within 48 h of its day (PLACE_HORIZON_MS, payments/sponsor-fulfilment.ts:29,143), so ads booked later do not appear in the schedule. This feed could fill the 'Other' row.
- Per-row failure and cost: scopeOf returns 400 no_channel_card for an orchestrator whose channel has no card (schedule.service.ts:89). useSchedule has retry:false and refetches every 60 s (api/schedule.ts:125-126). The grid needs an error state per row, and N rows mean N heavy schedule() calls a minute, each loading the source catalog and network context. That makes the aggregate endpoint more than optional at scale.

- Toast: ToastTone is only 'danger' | 'success'. success lasts 4 s (components/ui/Toast.tsx:10,32-33), which is too short for Undo. A toast with the same text replaces the existing one (:21), so the action toast needs its own TTL.
