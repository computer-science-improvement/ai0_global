## Deltas from the spec

- T1: the prompts.chat two-page fixture (`docs/testing/promptschat-fixture.ts`) was built in T1, not T2, because the T1 tests use it.
- T1: records are found at a root key or inside an object at a root key (`data.items`), not only at a root key; `records_path` shows `(root)` for a root array. The `json` answer also carries `first_record` and a short `outline` (≤ 20 records, `outline_more`) so the model can pick a section id; `web_fetch`'s own result cap (14,000) still holds for 100 big records (tested).
- T1: the field list is ordered filled fields first, then foreign keys and counters (`authorId`, `tags[].promptId`, `_count.*`), then empty ones, so the cap of 40 does not cut `tags[].tag.name` in the real prompts.chat shape. In that shape tags are `tags[].tag.name` (a `tag` object inside each item), one object deeper than the spec's example `tags[].name`; arrays of objects do not count as a level, so it shows up.
- T1: the intro section (root keys other than the records) has level 0 and no heading; records are level 1. A JSON document with no records array is one section; when it is over 6,000 characters it uses the ordinary large-document shape (outline of one section, first chunk).
- T1: link-header pagination is not done: `safeGet` returns no response headers (spec: only if it does).
- T2: `where` and `has` are accepted in `filter` and also beside it (the spec's examples show them at the top level); `buildPlan` folds both into `plan.filter`, which is what the card and the re-sync store.
- T2: the default `required` for JSON is one group, «the text or the picture» (`post_requires: [["prompt_text", "media_url"]]`, the form the prompts dataset of 083 uses), not one group per field. With one group per field the TEXT records (no `mediaUrl`) would never be postable and the spec's expected import of TEXT and IMAGE records could not hold. A `required` list passed by the model still means every field. Payloads and `options.list_import` now carry `required` as a list of groups or names (old ones are plain names and still read).
- T2: refs strip `perPage` / `per_page` / `limit` as well as the page and cursor parameters (changing the page size must not change refs); a record with a repeated id inside one run is counted once (pages overlap when a list grows between requests), a repeated title gets « (n)» as in 065.
- T2: the preview's counts are of the first page and say so (`pages.counts_are_of`); `pages_to_read` is a cap when the total is unknown (next link / cursor). The card summary says «about N entries» for a multi-page import (N = rows on page 1 × pages to read).
- T2: Apply's page 1 is the stored document (the one the model read, or a fresh fetch for a re-sync); only pages 2+ bypass the store. A cursor or next link that points back at an address already read ends the run, and an empty page is the end.
- T2: the row cap is applied exactly: the page that crosses `IMPORT_MAX_ROWS` is read whole and the rows are cut back to the cap. `pages_read`, `pages_total`, `stopped` and a Ukrainian `note` are in the Apply result; the dashboard card does not show `note` (no dashboard change was made).
- T2: incremental re-sync stops after the first page whose rows are all known (refs looked up by `list_ref`); a page with no rows after the filter says nothing and reading goes on. It is used for every re-sync, markdown lists have one page so nothing changes for them. Older records that changed on later pages are not seen by it.
- T2: no license hint is read from a JSON document (the hint looks for badges in markdown); the preview says no licence was given unless `license` is passed, and the runbook tells the owner to check the prompts.chat licence.
- T2: the caps read the settings through `env`, falling back to `process.env` (the settings overlay writes there), so the card handler registered in `editor.module.ts` needed no change.
