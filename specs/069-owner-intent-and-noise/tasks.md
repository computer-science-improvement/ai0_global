## Deltas from the spec

- **T1 · `prepareSeriesChange` option.** The spec names `{ pendingTables: [dataset] }`. The option is `{ pendingTables?: string[]; pendingEntities?: Record<string,string> }`: the entity of the dataset being created is needed for the format check of A3 (`datasetFormat(new_schema.entity)` against the series format), and the catalog already carries it for datasets that exist. A dataset the library already has keeps its own entity.
- **T1 · where the bundle lives.** The follow-up builder is a new file `docs/import-bundle.ts` (`buildBundle`, `thenLine`); `import-list-tools.ts` only calls it. `ImportPayload` and `payloadOf` are not touched: the tool spreads `then` into the payload (`{ ...payloadOf(…), then }`), so 070's `split_on` edits there do not conflict. The new zod fields are at the end of `ImportListInput`.
- **T1 · skipped items.** An item in `input.skip_then` is recorded `{ ok: false, error: 'skipped' }`; an item with `ticked: false` and no `skip_then` at all is `not_ticked` (A2). Both show on the card as «left unticked» / «not ticked».
- **T1 · limits.** At most 8 follow-ups per card (`MAX_FOLLOW_UPS`, checked at propose time with the registered kinds and unique keys); `disable_skills` takes at most 5 names. A name already switched off is dropped with a note (`follow_up_notes`), not an error. A system skill (`safety` / `isProtectedSkill`) is refused with `safety_skill`; the skill's owner handle is resolved over the orchestrator and its children, a shared skill goes on the orchestrator.
- **T1 · `sourceInSkill` is a heuristic.** It returns the first sentence that (a) has `provider=<x>`, (b) takes posts / prompts / content with a verb of taking and names a URL or «API», or (c) names a dataset (`library:x`, `data://x`, «dataset x») together with «only / instead of / лише / замість». A skill about how to use a row, or a link to put into a post, passes. Negated mentions («PromptHero не використовую») are not refused here: the conflict path of T2 handles them.
- **T1 · prompt text.** `buildComposerSystemPrompt` adds the source-change line only when there is no persona (the named agent's persona already carries it). The «do not re-announce a corrected answer» etiquette line from the code map belongs to FR-006 and comes in T5.
- **T1 · loadout.** Nothing to change: `import_list` is `chatOnly`, and loadouts only cover tools that are not chat-only, so a loadout never hides it from the composer. A test pins that (`import-list-tools.069.test.ts`).
- **T2 · where the code lives.** `skillConflicts` (pure) is in `agents/skill-warnings.ts` as the spec says. The part that reads the family and builds the items is a new file `agents/skill-conflict-followups.ts` (`conflictFollowUps`, `conflictsLine`, `conflictsForModel`, and `detachKey`, which `docs/import-bundle.ts` now imports and re-exports so an explicit `disable_skills` item and a conflict item share one key and never double).
- **T2 · clause.** A clause is a sentence, a line or a half of `;`, not a half of a comma, so «не бери з X, Y або Z» rules out all three. The price: «Бери з X, не бери з Y» rules out both X and Y. Written into the runbook.
- **T2 · matching.** A negated word meets a positive token when they are equal, or when it is the first part of a `nanobanana_prompts`-style key (5+ letters). Host labels use the second-level label (`bbc.co.uk` → `bbc`); a host without a scheme counts only with a common TLD, so `skill.md` and `e.g.` are not sources.
- **T2 · soft conflict.** «Different sources for the same format or series word» is: both skills have positive source tokens, none shared, and they share a format word from a fixed list (prompt, recipe, quiz, news, photo, meme, video, story, digest, quote) or a word of the skill names (5+ letters, minus stop words and spellings of a format word already there). It is a heuristic and the item starts unticked.
- **T2 · candidates.** Enabled skills of the orchestrator and its children (for a role agent: its parent's family), origin not `builtin`, not safety or `isProtectedSkill`, not the skill's own name, and, for a skill write, with at least one role in common with the new skill's `applies_to`. A shared owner-made (`global`) skill is a candidate and is switched off on the orchestrator. For `import_list` there is no role filter (a dropped source concerns every role).
- **T2 · budget.** Conflicts fill only what is left of `MAX_FOLLOW_UPS` (8) on an import card: with a series, a rule and 5 named skills there is room for one. A failed skill lookup never stops a card: the write_skill card goes without the items and the tool says `conflicts_error`; `import_list` adds a note to `follow_up_notes`.
- **T2 · wiring.** `buildAgentChatTools` gets an optional `agents` dep (`editor.module.ts`, one line); `BuilderToolDeps.agents` / `.skills` widen with optional `children` / `listForAgent`. Old wiring (tests that pass only `findShared`) keeps working and finds no conflicts.
- **T3 · demotion starts at the third note.** `runLength` counts the note being posted, so `DEMOTE_AFTER = 3` demotes the third note of a run (the first two ring, the third and later are info). Severity `action` only; `critical` is never demoted. The "owner acted" lookup is `owner_cards.resolved_by LIKE 'telegram:%'` on a card whose note is of the subject, since the run's oldest note; a failed lookup counts as "acted" (no demotion). A demoted note never falls back to the plain alert when the bot is inactive.
- **T3 · `standalone` gate flag.** A past-day `series_missed` (first miss found late) carries `gate.standalone`: same subject (so the repeat memory is shared) but no supersede, no edit in place. `NoteGate` also got `grow` (per-part step); `GateDecision` carries `runLength` / `runSince`.
- **T3 · where `reportedDays` comes from.** `SilentDaysWatch.check()` reads `<ref>|<day>` of the last 7 days' `series_missed` / `dark_day` rows from `agent_inbox` and passes it to `evaluateSilentDays` (`reportedDays`, optional, default none). A failed query is an empty set. 068's `load()` / `minPerDay` edits are not touched.
- **T3 · edit in place.** `InboxCardSink` may return `{ retargeted: <old note id> }`; `OwnerInbox` closes only the cards of the other superseded notes, in a `finally`, after the sink. The race between the supersede UPDATE and a sweep is accepted (a sweep that closes the old card first makes the sink fall back to a new card). A retargeted card keeps its old `critical` flag (a critical note never retargets, but a card that was critical can be edited by an action note). `supersede()` is kept for callers that only need the old behaviour.
- **T3 · event watch.** `EventWatchDeps.inbox.markRead` and `openNotes` are optional; without them nothing is closed (old wiring works). The notes it reads are the unread `event_not_covered` rows with ref type `story_event`.
- **T3 · daily block.** `repeatingSubjects` recomputes the demotion rule from the rows (nothing is stored): a subject appears when its unbroken run has at least 3 notes, its newest note is not critical, at least one note of the run is not info, and no card of the run was resolved from Telegram.
